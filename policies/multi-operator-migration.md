# Policy: Multi-Operator Migration

This is the authoritative operational runbook. It governs isolated rehearsal and any separately authorized adoption; it does not authorize live transition. Research and rationale remain in [the collaboration brief](../briefs/multi-operator-collaboration.md).

As of 2026-10-29, `bin/multioperator` implements committed-source transition rehearsal, new-record maintenance, canonical phase selection, accepted-close and indexed-byte validation. It deliberately has no live-adopt, ownership-service, Git-reset, remote or policy-switch command. The rehearsal transforms a committed tracked snapshot, including symlinks confined to that snapshot, into a new absent destination. Existing dirty files and ignored runtime evidence are neither overwritten nor falsely described as converted. A successful rehearsal is capability evidence, not an adoption decision or a qualified product phase.

## 0. Unified migration runbook

This is the single end-to-end entrypoint. The numbered steps link to detail below; scripts mechanize conversion and validation, while the owner supplies scope, custody and consequential decisions. **Implementation boundary:** conversion, maintenance and receiving phase/evidence/staged-byte adapters are implemented and exercised on isolated current structures. Every actual cutover still proves steps5–8 against its own complete candidate and custody. The donor’s scoped delivery receipt establishes its actual adoption; script presence and a declaration do not. Other projects enter through canonical Teach/Learn, never a separate unapproved rollout.

1. **Select the route and owner.** For Starter's first cutover, use its separately authorized canonical-owner migration scope. After Starter has actually adopted, invoke `/teach <project>` or `$teach <project>` from Starter, or `/learn <starter>` or `$learn <starter>` from the receiver. The invoking primary presents the ordinary concrete transfer plan and retains the receiving owner's authority and project adaptations. Run `bin/multioperator transfer-preflight --entry teach --donor <adopted-starter> --recipient <target>` (use `--entry learn` from the receiver). It must select the expected migration or maintenance route; declarations never grant writes or prove adoption. A legacy/rehearsal donor or unresolved receiver refuses. See §6.
2. **Preflight the exact committed source.** Record source commit and path, current ownership, clean/dirty attribution, terminal commands/reviewers/native callbacks and durable evidence locations. Settle unique work without overwriting it. Use a boundary that leaves no unfinished consumed review across the id change; otherwise defer cutover rather than reset its budget. Observe the receiving host's Claude version: absent is ungated; installed requires a successful parseable version at least2.1.290. Keep remaining configuration caveats visible without changing files/settings or inventing eligibility gates. See §1, §4 and §7.
3. **Prepare the owner-reviewed conversion input.** Run `bin/multioperator inventory --root <source>`. Write a durable JSON map containing `writer`, the complete numeric-id→permanent-slug `phases` map and exact old-tool `retirements` preimages, plus any explicit owner/checkpoint fields. Check parents, dependencies, affected references, original history and project customizations. Identify which old-only tools leave, which shared tools remain, and the exact live adapters/proofs still requiring cutover. Unknown custody or an unreviewed custom recipe is a concrete stop, not permission to copy a donor wholesale. See §1 and §6.
4. **Run and examine the isolated rehearsal.** Run `bin/multioperator rehearse --source <source> --mapping <map.json> --output <new-absent-target>`. On that output run `bin/multioperator validate --root <target>`, `bin/multioperator render --root <target> --check` and `bin/multioperator audit-retirement --root <target>`. Inspect the retained manifest, constitution/version/caveat receipt, retirement report and adoption-blocker inventory. Independently verify exact original-log reconstruction, complete phase/parent/dependency/reference conversion, regular primary AGENTS with no top-level CLAUDE, retired-tool absence and unchanged live source. Exercise positive/refusal and maintenance cases on the actual receiving variant. Any failure stays preserved; no failed output becomes adopted. See §2–7.3.
5. **Complete the atomic adoption candidate.** This is the explicit boundary beyond structural rehearsal: adapt every affected shared phase selector, policy/skill, candidate/close/acceptance/report reader, command/hook caller, fixture and contract inventory to the new schema, retiring old-only callers and tests without aliases. Preserve product content, raw evidence, consumed budgets, failed/rejected history and local customizations. The converter performs structural rewrites, and the shared adapters implement the current schema. Its conversion-time pending-adapter inventory still requires explicit receiving-owner resolution and variant-specific qualification, never a waived marker. Apply recipient-local proof admission/retirement obligations; donor proof judgments do not transfer. See §3–7.6.
6. **Accept the complete candidate.** Repeat the three target validation commands from step4, execute the target's actual catalog/parity checks, applicable focused and refusal proofs, ordinary acceptance checks and final full gate on the complete candidate. Verify retained bytes and source/native/candidate joins where relevant; an imported completed marker or arbitrary acceptance JSON is not a product decision. Resolve every material adapter/refusal before claiming operational readiness. Version success is not instruction-loading proof; report actual session-loading evidence separately. No model review, extra allowance, hook installation, grant or permission is inferred. See §3 and §7.
7. **Cut over and verify delivery under existing authority.** At the released safe boundary, apply the coherent accepted candidate through the receiver's existing staging/commit/delivery rules, using explicit paths and preserving project-specific content. Confirm final identity/status, absence of dual authorities and obsolete executables, ordinary new-structure commands and actual active-owner/session instruction state. Only then record actual adoption and release work. Do not relabel rehearsal success as this step or infer a new remote/publication permission. See §5.
8. **Rollback or maintain deliberately.** If adoption fails, stop new work, retain the failure and let the authorized owner use normal history-preserving Git reversal or a forward fix; no automatic reset, extra backup framework or permanent compatibility reader is provided. Once adopted, use the new `add`, `order`, `event`, `append`, `validate` and `render` commands, and future Teach/Learn maintenance detection. Preserve event/log immutability, evidence and ownership boundaries. See §5 and §8.

The runbook is the operational sequence, not an execution receipt. The current implementation includes the shared adapters, but a receiving project still qualifies its own actual adoption in steps5–7. Acceptance evidence must state which steps were performed and on which exact source/target, rather than presenting this checklist itself as execution proof.

## 1. Inventory and declare the boundary

The owner establishes the exact source commit, clean/dirty attribution, current writers, active commands, native callbacks and retained evidence homes. Keep unique uncommitted work within its existing custody; commit or otherwise settle it through the project's normal authorized workflow before actual cutover. Git history is rollback. Do not create a second backup/archive framework, force-clean a checkout or rewrite valid chronology.

Build an explicit complete map from every current numeric phase id to one permanent three-word slug. The converter refuses missing mappings, duplicate targets, file/table disagreement, absent parents and invalid dependencies. Retired historical numbers are not reused or silently equated to a current phase; their dated decoder notes and original wording stay history. Choosing meaningful ids, owners, retired-work dispositions, delivery model and a reachable claim service is operator judgment. A caller-supplied writer/claim label is attribution, not authentication or an access grant.

The migration input is JSON with `writer`, `phases`, optional `owners`, optional `active_checkpoints`, exact `retirements` preimages for old-only tools present in the source, and `tool_replacements` preimages for any differing already-present migration tools. An unexpected, unused or changed tool replacement refuses; the source commit and owner-approved recipe bind that narrow update. `multioperator inventory --root <source>` reports the observable old-only/shared inventory without changing it. An in-progress phase needs an explicitly named owner and a checkpoint carrying `terminal: true` plus a retained `evidence` reference before even rehearsal conversion. Those fields record the owner's observation; the tool cannot establish machine-wide quiescence. It does not resume a process or clear a native callback.

## 2. Rehearse mechanical conversion

Run `bin/multioperator rehearse --source <checkout> --mapping <durable-map.json> --output <new-absent-directory>`. The output is staged in an owned disposable directory, fully validated, then published by one directory rename. Existing destinations, escaping archive symlinks and malformed input refuse. The source repository is read-only throughout. A private manifest records the exact source commit, archive/tool digests, id map, original log byte count/digest and active imports, with `adopted: false`.

The converter moves phase bodies into `plan/phases/<id>.md`, rewrites frontmatter `id`, `depends_on` and `informs`, derives direct `parent`, and assigns exact rational order keys in original execution order. It emits one imported genesis event per current phase. An imported completed marker records the old declared state; it is not retrospective acceptance or a new seal. The old numeric files are removed from the rehearsal, not retained as compatibility aliases. Qualified current Markdown file links are mechanically rewritten, including relative-depth changes and fragments. Ambiguous unqualified prose and historic numeric references are not guessed at.

Historical log conversion splits only genuine dated entry headings outside fences. Each immutable Markdown entry has a small frontmatter envelope with identity, writer sequence/predecessor, exact body digest and original byte offset. Every original body byte, timestamp spelling, failed/parked outcome and quoted example is preserved. Unknown authorship is explicitly `unattributed-import`; conversion does not attribute old work to the migration operator. Import order uses original offsets, so old cross-host clock disagreements do not become newly invented timestamps. Concatenation reconstructs the entire original log exactly, including its preamble. There is no duplicate legacy log or rollback archive; original Git history remains the source for the old layout.

The plan discovery document preserves handwritten context while removing the old status table and dependency graph as authorities. Remaining old procedural prose and extensionless executable readers/writers appear in `collaboration/adoption-blockers.json`. Raw execution/advice packets, consumed review ledgers, reports, lessons and user-action history are never mass-renamed or rewritten. Old links in immutable history are interpreted using its source commit and dated mapping, rather than by a permanent alias reader.

## 3. Qualify before any live cutover

Acceptance of the mechanical conversion requires exact original-log reconstruction; complete one-to-one phase identity mapping; correct parents, dependencies and known links; unchanged source tree/status/ownership; explicit active-import limits; deterministic view regeneration; and negative cases for invalid mappings, unsafe/occupied destinations, stale/forked events, cycles/order violations, missing or mutated retained evidence and malformed chronology. Rehearse against faithful current project structures as well as bounded synthetic variations. Preserve failures and their actual diagnostics. Tests run on new owned copies; none supplies authority to change live records.

A live migration additionally replaces every affected policy, skill, phase selector, frontmatter/table validator, renumberer, log writer/checker, execution/report reader, command/acceptance adapter, hook caller, fixture and independent contract inventory in one qualified candidate. The generated blocker inventory is a search lead, not proof that every semantic caller was found. Review the actual implementations and exercise their ordinary positive/refusal paths; do not turn a grep match into a completeness claim. A project-specific application path can be untouched while all its governance callers still need this atomic cutover. No live dual-format fallback is proposed.

## 4. Active work and review-budget continuity

The smallest supported live boundary is after active work has finished under its original authorities: commands/reviewers/native callbacks terminal, accepted or truthfully parked closures preserved, unique work and ownership settled, and no unfinished phase requiring a consumed review allowance across an id change. Importing an active snapshot into a rehearsal is forensic conversion only, not permission to continue it through the new identity.

A phase with consumed PLAN/CODE invocations cannot acquire a fresh budget merely because its display id became a slug. Existing native/run/candidate/registration joins and original budget keys remain exact. Until a separately specified and qualified identity-to-budget continuity adapter exists, finish that phase in the old structure or defer live cutover. Do not invent new phase scope, reset claims, reconstruct missing runs or relabel a failed call as unstarted. A project that needs genuinely active cross-format continuation has that concrete additional prerequisite; this rehearsal does not claim it was implemented. Never hot-patch a frozen governing snapshot or rewrite a closed run's tools to make the transition appear compatible.

## 5. Cutover and Git-only rollback

The owner selects the actual adoption boundary and delivery method, records any project-specific consequential rulings, and applies the rehearsed mechanical conversion together with the qualified caller/policy changes. Commit the coherent candidate and pass its normal focused, acceptance and full handoff gates. Verify current owner/session instructions loaded the new authority; a file edit alone does not prove runtime adoption. Before releasing work, verify source identity, generated views, absence of dual authorities and exact evidence/budget continuity again. No new hook trust, grant, remote, rebase or security permission is inferred.

If cutover fails, stop new work and diagnose against its Git diff and retained failing evidence. The owner chooses an ordinary history-preserving reversal or forward correction through the existing Git authority; the scripts do not automatically reset, rebase, restore or discard uncommitted data. Retained rehearsal/evidence bytes serve qualification, not a separate rollback framework. Successful conversion is not successful adoption, and successful adoption is not human/product acceptance.

## 6. Old-tool retirement and the future transfer entrypoints

The isolated conversion retires the numeric renumberer and the single-file log append, relocation, prefix, chronology and composed-check executables. Its explicit inventory distinguishes those old-only tools from the still-shared body/Lessons parser, generic execution/index normalization, candidate/evidence machinery, aggregate gate, staged hook and catalogs. Every removed executable needs an exact approved preimage in the migration map's `retirements` object; unexpected or missing entries refuse. This is a recipient-owned recipe, not permission inferred from a filename. The dedicated renumbering test leaves the target, the mixed log-control scenario is rewritten to retain normalization coverage, and executable/lint/catalog/caller/test references are cleaned. No obsolete command alias or wrapper is kept. Shared semantic workflow adaptation and recipient-local proof admission/retirement remain explicit live-adoption work, rather than donor judgments copied into a receiver.

The replacement staged validator snapshots actual indexed phase/event/log/manifest blobs, checks unchanged committed immutable records, verifies retained referenced bytes and rejects unresolved indexes, deletions, rewrites or concurrent HEAD/index movement. It does not substitute the working-tree version for what will be committed. New terminal log bodies retain the Lessons witness requirement. Retirement audits verify physical absence and removed operational-reference tokens; explicit deletion selectors, negative-test inputs and immutable historical text are distinguished from callers. Token absence alone does not prove that every shared caller's new schema semantics is accepted, so that separate limit stays visible in the target's adoption report.

After the canonical template has actually migrated, receiver migration is triggered by `teach <project>` from that template or `learn <starter>` from the receiving project, using the ordinary skill invocation forms for each harness. There is no separate manual-only migration channel. `multioperator transfer-preflight --entry teach|learn --donor <source> --recipient <destination>` provides side-effect-free detection: legacy or rehearsal donors, malformed/partial layouts, a receiver's unresolved rehearsal and self-transfer refuse. A declared adopted donor with a pre-migration receiver selects migration rehearsal; a declared adopted receiver selects maintenance.

Detection deliberately returns `mutation_authorized: false` and `adoption_verified: false`. A marker is a declaration, not proof that Starter migrated or that any recipient owner approved writes. The invoking skill independently verifies actual donor adoption/candidate, recipient custody and current content/runtime, the safe phase/native/review boundary, exact retirement recipe and the existing concrete Stage3 transfer-plan approval. It then invokes rehearsal, evaluates its exact conversion/retirement evidence and completes recipient-specific atomic adaptation and ordinary acceptance/full gates before actual cutover. No raw donor/recipient runtime packets, local proof judgments, grants or permissions are transferred. The classifier does not authorize another repository’s migration. Ordinary compatible capability transfers remain usable; whole-methodology updates from an actually adopted donor to a legacy methodology receiver include this migration in their concrete owner-approved plan.

## 7. Primary constitution and the installed Claude gate

The migrated target has a regular primary `AGENTS.md` and no top-level `CLAUDE.md` file or symlink. The converter preserves the original constitutional rules, then rewrites exact repository-root filename references and the target catalog/parity checks. It does not create a different brief-index convention, remove local/ancestor instructions or change software, plugin, telemetry, managed policy or security settings. Conflicting constitutional bodies refuse for owner reconciliation. A pre-transition source retains its constitution until its owner’s authorized cutover; the adopted target has only the regular primary AGENTS file.

If Claude Code resolves on the invoking host, its successful, parseable stable version must be at least **2.1.290**. An absent executable has no Claude version gate; a failing or unknown version query is not compatibility evidence. The rehearsal and migration-route preflight record the observed version and minimum, explicitly marking instruction loading as not observed. A remote recipient must run this check on its own receiving host; the donor's version is not a substitute.

Native AGENTS support first appeared in 2.1.277. The selected floor includes 2.1.281's provider/gateway/telemetry-disabled fixes and 2.1.290's subdirectory @-mention omission and instruction-symlink/Read-denial fixes. Version alone does not prove loading: project or ancestor `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` can suppress default AGENTS loading; user-global `~/.claude/CLAUDE.md` and managed instructions do not. A disabled built-in plugin or first upgrade session from 2.1.276 or older can also affect loading. Record these as runtime caveats and verify actual instruction loading at adoption; do not invent extra eligibility/version gates or silently alter those files/settings. Isolated fixtures test the version boundary and preservation behavior, not a live harness's constitutional loading.

## Retain evidence without replacing private indexes

Preflight private evidence destinations independently from tracked source preimages before cutover. A capture index is an append-only history of retained bytes, not a file to replace from an isolated candidate. Verify each content-addressed object and size, preserve existing objects and the exact index prefix, then append only verified new references through the owning retention procedure. Different index bytes alone do not establish conflicting artifact bytes. Refuse changed content, missing originals or uncertain ownership; preserve the stopped operation and resume only the bounded verified retention step. Do not rerun an already-applied source conversion or copy an entire runtime/evidence directory over current state.

## 8. Transition ends; maintenance begins

The maintenance commands read only the new schema; they do not contain legacy aliases or a permanent numeric/log compatibility branch. `validate` checks unique phase identity, complete references, acyclic parent/dependency graphs, real total-order constraints, one predecessor chain per phase, valid lifecycle edges and owner handoff references. Concurrent successors are preserved as conflicts and refused; a deterministic renderer never silently picks the furthest state. `next` is a selection per owner, not an exclusive lease; multiple operators can queue independent work. Starting/handoff still requires external coordinated claim/release evidence under the project's selected mechanism.

`add` accepts one new phase document, creates a not-started genesis and refuses identity collisions or invalid graphs. Both new files belong in one Git commit. Interrupted partial publication remains visibly invalid and must be settled through normal custody/Git procedures; it is never reported as success or silently cleaned. `order` changes only the exact rational key after whole-graph validation. Phase-body prose edits retain normal Git review/merge semantics.

`event` appends a fresh predecessor-bound record after validating the proposed fold; duplicate/replayed/stale inputs refuse before publication. A new completion requires a retained acceptance-artifact path/digest whose bytes are verified. The accepted-close adapter binds real candidate, authority, phase, gates, retained execution/review-ledger prefixes and captured custody. Fresh publication revalidates with the receiving qualified code; historical validation retains the original accepted inputs without requiring today’s product to equal an old product. An arbitrary JSON receipt, renderer screenshot, imported completed marker or caller-written claim is not product acceptance.

`append` adds a new immutable Markdown log entry with a named current writer, contiguous per-writer sequence/predecessor, canonical timezone-aware UTC and body digest. Regressing clocks, gaps and tampering refuse. Cross-writer timestamps are presentation order, never exact causal timing. Existing finalized execution traces remain the timing authority. `render` builds ignored plan/log views; `render --check` refuses stale or missing views. Views are reproducible projections and never written back as authoritative state.

## 9. Capability and adoption evidence remain separate

The implementation supplies committed-source conversion, old-only tool retirement, new-format maintenance, canonical selection, owner/claim-bound accepted completion, parent acceptance chains and indexed-byte validation. The tests exercise faithful old source conversion, actual synthetic phase acceptance and staged refusal, retained-byte and original-ledger integrity, and finite concurrent-write cases. These are tooling capabilities, not authority to migrate every receiver or proof that a live harness loaded its constitution.

Each adopting owner records exact source/mapping/preimages, terminal boundary, applied adapters, preserved history and budgets, local proof judgments, current-candidate checks, final full gate and actual instruction-loading result. Keep pending or unavailable native-loading observations explicit; version metadata is never substituted. No default push, software update, grant, hook installation, identity migration or remote rollout follows from this policy. Git remains rollback and the current record format is the only maintenance format; old-format parsing exists only in the explicit transition path for receiving projects.
