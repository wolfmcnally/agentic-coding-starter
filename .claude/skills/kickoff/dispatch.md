# Kickoff — Shared role dispatch

## Authority-mode interpretation

Read the frozen workflow mode. Product primary mode dispatches only independent advisory reviewers, retains planning/coding on the invoking instance, and accepts through a current primary decision plus required checks. A reviewer verdict or remaining suggestion cannot block it. Second review/critique requires recorded cause; two passes per stage is the default maximum across continuations, subject only to the explicit single-use User exception in [orchestration-evidence.md](../../../policies/orchestration-evidence.md#single-use-owner-exception). Candidate changes require truthful delta assessment and fresh tests, not mandatory additional advice. Delegated product mode retains the approval/revision procedures below. Methodology work follows the separate primary one-shot route with no delegated role or independent review and with commit/push authority after required checks.


Read this resource before executing its branch. Enter through [SKILL.md](SKILL.md); its resource table defines the order. Before any failure, resume or operator-input branch, read [recovery.md](recovery.md).

## Select the supported transport

Prefer an available supported cross-harness launcher and communication surface over direct native harness launches. Apply [optional cross-harness coordination](../../../policies/role-models.md#optional-cross-harness-coordination) before choosing a dispatch mechanism. Launch and messaging capabilities are independent; prefer supported communication even if the role uses direct execution. Verify the intended current recipient, exact role scope and the selected surface's actual lifecycle/evidence support. Record the route and qualification basis or concrete fallback reason in existing run artifacts.

When no supported cross-harness launch path is available, use the existing direct native dispatch path. Optional absence does not block kickoff or authorize installation, credentials, identity/access changes, a different model or another role. The direct-path procedures below remain fully supported. An integrated path must carry the same generated execution contract through the existing enforcing watcher or a qualified supported host interface; do not replace its controls with prompt assurances or fabricated receipts. Message acceptance and delivery are not terminal work or operator approval. A denied or uncertain launch is not retried through another transport; inspect actual state and follow governed recovery before any authorized retry.

Before every role attempt, atomically run `$EVIDENCE_TOOL register-role-attempt` with its stable operation (`role.plan`, `role.plan-review`, `role.implement`, or `role.code-review`), attempt, role, harness, resolved model/effort, reason, and a per-attempt `--output` file directly under `$RUN_DIR`. Never pass the append-only `role-attempts.jsonl` ledger as a registration.

For the direct external-CLI path, pass that file to `$WATCHER_TOOL watch --telemetry-role-registration <file>`. It supplies the authenticated trace, root span, operation and attempt; do not reconstruct or repeat those values. Invoke the pinned watcher executable directly so its declared script dependencies are provisioned; those dependencies are outside the project environment, so do not run the watcher through `./bin/python`. Other tools follow their generated invocation contracts, including project-interpreter recipes when their dependencies are provided there.

Generated Claude calls use print mode with native background tasks disabled: a print process exits after its response and cannot provide an interactive session's later completion callback. Keep role work within the watched invocation. This lifecycle setting does not grant additional tools or filesystem access.

A launcher refusal before launch consumes nothing: no span opens, no dispatch row is written and no advice pass is charged. Correct the command and relaunch the same registration; do not register the next attempt number, and the registrar refuses one while an earlier attempt of that operation was never dispatched. Only when that registration can never be launched, retain the launcher's refusal output inside the run directory and record the fact with `$EVIDENCE_TOOL record-unlaunched-attempt --run-dir <run> --registration <registration.json> --refusal-artifact <retained refusal>`, then register the next attempt.

For an external venue using direct dispatch, write the role prompt to a file and invoke `$WATCHER_TOOL watch`. The watcher generates the complete Claude or Codex command from routing metadata, including access stance, structured-output schema, credential scrubs, recursion guard, artifact wiring, and timeouts. Never hand-write the child command; use `$WATCHER_TOOL render-command` for inspection. For a native venue, validate the registration, open the same intelligence span, open its nested wait span only after dispatch acceptance, then close both truthfully and record their ids with `record-role-dispatch`. Rejected dispatches close intelligence as error 127 and create no wait. Every retry, resume, rescue, reexecution, or fallback gets a new immutable registration and attempt number.

The watcher is the default and the only launcher this skill needs. If the owner directs, for this task, a particular reviewer or another launcher, follow [owner-directed review](../../../policies/orchestration-evidence.md#owner-directed-review-outside-the-watcher): record the verified direction with `$EVIDENCE_TOOL record-owner-directed-review` before registering, register exactly the directed reviewer, run `$EVIDENCE_TOOL start-advice` yourself, build both spans from the generated span recipe, open and close the dispatch as for a native venue, record the launcher's response with `$EVIDENCE_TOOL attest-directed-launch`, then ingest the report with `--input`. Record anything you did not observe as `unknown`. Never register a directed reviewer as the frozen one, and never launch the same attempt through the watcher as well.

Every dispatch records product identity before and after the role. Bookkeeping alone does not move it; an active change requires review against the current product candidate, with no drift-acceptance exception. Declared-authority and explicitly reviewed-bookkeeping checks remain binding under `policies/orchestration-evidence.md`. **For an external role you do nothing:** `$WATCHER_TOOL` captures the open candidate immediately before it spawns the child and records the row only after the child terminates. **For a native role**, and only then, run `record-role-dispatch --state opened` (with `--dispatch-candidate` set to the id `current-candidate` printed immediately before you dispatched) before launching the role, and append the accepted or rejected terminal amendment after the role has returned — not while it is running, or both candidates describe the same instant and a mid-role write becomes invisible.

Read the canonical role body before dispatch and require the role to read it. Deliver mandatory execution contracts from their enforcing sources: the watcher supplies research/access directives, schemas, credential handling, routing and budgets; never reconstruct weaker substitutes from memory. Native dispatches use the generated `span-recipe` commands and the same resolved research directive and output contract. Skill discovery, root injection, a role read and a stage-resource read are distinct events; a link alone proves none of the reads.

All roles use fresh run-scoped artifacts. Preserve exact response bytes; the watcher owns its output paths. A coder writes only its assigned scope and never commits or pushes. Independent review requires a separate review context even when model and vendor match.
