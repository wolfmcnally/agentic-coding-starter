## 2026-11-20 02:56 — END — METHODOLOGY — Release 1.9.0 prepared: a release requires one clean checkout, and worktrees are owned from creation

Scope: the operator's direction of 2026-11-20, relayed by the coordinator: "This must get fixed in Starter on MAIN and released"; "it needs to be a mechanical check. No extant work trees or other dirt before a release"; and "a repo's coordinator needs to not let it get that far." The cause was a product release in a derived project, tagged from a clean checkout while an existing registered worktree of the same repository held unexamined tracked and untracked changes. One bounded change and its release notes. No tag is created here; no recipient and no other repository was touched, and nothing about the earlier release was repaired.

Changed:
- A new read-only executable, `bin/check-release-worktrees`. It passes only when Git lists exactly one registered worktree, that worktree is the checkout being released, and its status is empty for tracked, staged and untracked paths. It refuses any other registered worktree, clean or dirty, and reports each one's observed state; it refuses locked, prunable, bare and missing registrations, a directory that is not the top of a checkout, a record without a commit or without exactly one of branch and detached, and a listing that changes while it is read. A failed Git command is an error and is never read as clean. It reads the NUL-delimited listing and status, so a path with spaces or newlines is read exactly. It never removes, prunes, moves, resets or unlocks anything.
- Procedure. The human-judgment policy requires the check at the start of release preparation and again immediately before each tag or publication, states that it proves hygiene and not artifact correctness, and keeps it out of the ordinary full gate. The same section now requires that a temporary worktree's owner and purpose are recorded at creation, that the receiving coordinator confirms delivery or preservation and retires eligible worktrees with nonforced commands at handback, and that a dirty or abandoned handoff keeps a named owner and a precise hold. The kickoff close resource, the manual, the tools catalog, the stamping copy list and this template's release policy carry the matching text. No supervisor, timer or automatic deletion was added.
- Proofs. Sixteen proof cases in a new family, each observed red against a planted defect and green on restoration: a sole clean checkout passes; tracked, staged and untracked dirt each refuse and leave the repository unchanged; a clean extra and a dirty extra worktree refuse with distinct states and still exist; a path with a space and a newline is reported exactly once; a missing and a locked registration refuse and stay registered; a run from a linked worktree refuses; a failed listing and a failed status are errors; three records lacking identity fields refuse; a directory below the checkout top refuses.

Not wired into `bin/check`: the tool is not in the gate's required-executable or lint lists, because it is a release step and not a gate lane; it was linted and formatted by hand with the project's configuration.

Release: `RELEASES.md` gains the 1.9.0 entry and transfer list. Minor increment, a new methodology capability.

Verification: the new test file, the changed-path selection, and the release gate with every proof run on the exact tree. Git listed one registered worktree and a clean tree for this repository when the work began; the check is run on the committed tree and again immediately before the tag.

Not done: the signed tag, which waits for the operator's approval.
