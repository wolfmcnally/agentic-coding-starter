The `refactor` skill has three scopes. Every one of twenty-one evaluation sessions used the same one, a named target on a small package. The skill was delivered with the other two never run. The first real use of `survey`, a dry run on a derived project, showed its scope sentence was wrong: "the whole deliverable" sent both models into a retired product that the project's own conventions reserve for a separately approved decision, and one of them spent most of an eleven-minute run there.

The primary then compounded it when scoring the dry run. It checked whether the reported claims were true, found that they were, and called the run a success; it did not check whether the claims were in scope, which the project's instruction file had already answered. The operator caught both.

What should be done differently: before a skill is delivered, list its scopes, modes and branches and run each at least once on input where that branch matters; report any that were not run as unverified, by name, in the delivery record. An evaluation that scores one branch many times says nothing about the others.
